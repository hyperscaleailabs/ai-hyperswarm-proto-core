# Observability at Scale: From Trajectories to Operational Intelligence

> For: DevOps / SRE level - operational concerns, scaling, monitoring, cost
> From: [[2026-08-08-synthesis-after-20-lessons]]

Twenty iterations in, the autonomous loop has moved from "can we observe what's happening" to "we have more data than we know what to do with." Trajectory capture is working; we now have structured logs for every agent decision. The next phase is turning that raw data into operational signal without drowning in volume.

## Operational facts on the ground

**Trajectory volume and cost.** We're capturing ~7KB per agent execution. At 5 iterations per block and ~20–50 agent invocations per iteration, that's roughly 700KB–1.7MB per block, or ~28MB–68MB per review cycle. Storage is manageable (a multi-year corpus fits on one disk), but it's not free. Query performance for large-scale aggregations (e.g., "show me all decisions where model=haiku and outcome=fail in the last 2 weeks") is currently in the 5–30 second range on commodity hardware.

**CI/CD green rate: 80% (16 pass / 4 fail).** Most iterations complete successfully; failures are recorded and analyzed. One recent failure (governance artifacts for block 41343) demonstrates that even automated systems can trip on edge cases. The lesson: failures are data, not disasters, as long as we capture them.

**Model selection is working, mostly.** Light models (Haiku) are assigned to synthesis and categorization tasks. Heavy models (Opus) handle complex tickets. The heuristic isn't perfect — occasionally a ticket is routed to the wrong tier — but we have trajectories to spot and learn from those decisions.

## The new operational reality

**From logs to dashboards.** We now have:
- A trajectory store (queryable, structured)
- A cycle journal (durable, resumable across crashes)
- A knowledge base (wikilinked, Obsidian-ready)
- Lesson records (outcome + metadata per iteration)

What's missing: a dashboard or summary tool that lets a non-technical person ask "what happened this week" and get a one-page summary instead of reading 20 JSON files and a git log.

**Compliance and retention.** Trajectory data contains decision rationale. If a decision is later disputed, we have a full audit trail. That's good for accountability; it's also a liability if someone's personal data is captured. We need a policy on what gets logged, how long we keep it, and who can access it. Currently: undefined.

**Replay validation is the new pre-deploy step.** Before shipping a change to model selection or the core orchestrator, we can validate it against historical trajectories. This was theoretical last week; this week it's operational. Replaying 100K lessons takes ~1 hour; that's fine for nightly validation but not for pre-commit checks.

## Operational toil (what still hurts)

**Manual lesson annotation.** Every PR produces a lesson; lessons are currently edited by hand (the agent writes an initial draft, then a human fills in details). For 20 lessons in 8 days, that's manageable. At 100 lessons per week, it becomes a burden. We need autogenerated templates that capture 90% of the detail.

**Knowledge base navigation.** 20 articles, 4 whitepapers, 20 lessons, all in Markdown with wikilinks. An Obsidian user can explore this; a non-user gets lost. We need either a web UI or better tooling to navigate without local setup.

**Quota and cost tracking.** We have a ledger (iterations.jsonl); we know which model was used for each iteration. What we don't have: a dashboard showing token cost per merged PR, cost trend over time, or alerts if we're on track to exceed budget. That's urgently needed once models go metered.

## What to watch (operations roadmap)

1. **Storage growth.** If we keep trajectory data forever, storage will become expensive. Define a retention policy (e.g., keep for 1 year, archive older, purge after 3 years). Automate archival.

2. **Query performance.** As trajectory data grows, aggregate queries will slow down. Consider indexing common query patterns (e.g., model distribution, outcome distribution by kind, cost by tier).

3. **Replay infrastructure scaling.** Currently one-off; should be scheduled and continuous (nightly validation of model-selection heuristic against last week's trajectories).

4. **Alert thresholds.** Define thresholds for "something is wrong": fail rate > 20%, cost per PR > $10, average model selection latency > 100ms. Automate alerting.

5. **Data privacy.** Audit what's being logged (does trajectory capture any user data, API keys, secrets?). Define a retention/purge policy and implement it.

The infrastructure is solid. The question now is whether trajectory data becomes a load-bearing part of operations (dashboards, alerts, replay validation) or whether it remains information-rich but effort-intensive to use.
